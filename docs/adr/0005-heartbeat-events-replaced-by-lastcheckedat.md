# Heartbeat events replaced by a single `lastCheckedAt` pointer per Listing

ADR 0003 and the PRD both claimed the processed layer "stays small by construction — it only grows on actual price/availability changes, not on every scrape." In practice this was wrong from the start: every Scrape Run that observed a Listing unchanged appended a `type: 'heartbeat'` entry to that Canonical Fish's `events[]` array, identical in shape to a real Change Event except for the tag. A partially-backfilled real Listing (issue #78's backfill, deliberately stopped early to let this fix land first) already had 139 events — 128 Heartbeats, 11 real changes — at 46KB for one Canonical Fish file. At full ~10.5-month historical depth across ~12,000+ tracked Listings, growing by one Heartbeat per Listing per day forever, this would have ballooned the `data` branch (which this project's whole architecture — ADR 0003 — depends on staying small enough to live in git indefinitely, with no database) into hundreds of MB to low GB, with no ceiling.

**Decision**: a Canonical Fish's `events[]` array now only ever receives `type: 'change'` entries — exactly the real price/availability changes it always should have been limited to. In their place, `CanonicalFishHistoryListing` (the per-Listing metadata already carried alongside `events[]`, per issue #3) gained a `lastCheckedAt: string` field, updated in place on every observation of that Listing — whether or not anything changed. This is a single, constant-size pointer per Listing (not an ever-growing array) that answers the one question a Heartbeat ever actually answered: "was this Listing still being checked, and still in this state, as of some date?"

This changes the frontend's price-history chart (`PriceHistoryChart.tsx`) in one real way: a variant's line used to get a point every single day via the dense Heartbeat trail, which issue #75 already stopped relying on for gap-detection (it broke lines purely on hard evidence — `available: false`, the sold-out price placeholder, or a variant vanishing from a later observation — never on a silent gap's size or cadence) but still implicitly used for "how far does this line visually extend." Without Heartbeats, a variant unchanged for months would otherwise render as a line stopping dead at its last Change Event, looking abandoned rather than "still tracked, unchanged." The chart now extends a variant's final run flat out to its Listing's own `lastCheckedAt` instead — the same authoritative, single pointer, doing double duty as both "stop writing an unbounded array" on the backend and "draw the line out to today" on the frontend. A variant whose last known state is already a gap is left exactly where the evidence says it should end; `lastCheckedAt` only ever extends an *in-stock* line, never bridges past a confirmed out-of-stock state.

**Migration**: every history file already on the `data` branch at the time this landed had Heartbeat-bloated data from the regular daily pipeline plus issue #78's partial backfill (aquahuna, monster-aquarium, ck-fish-world, and a small aquatic-arts sample). A one-time pass (`npm run migrate-heartbeats` / `src/lib/migrate-heartbeats.ts`) compacted every file in place: for each Listing, `lastCheckedAt` was backfilled from the latest Heartbeat's timestamp (or the latest Change Event's, if no Heartbeats existed — equivalent, since events are always append-only in `observedAt` order, to simply the chronologically last event for that Listing before stripping), then every `type: 'heartbeat'` entry was removed. `type: 'change'` entries were left completely untouched, in content and order. Run against the real `data` branch, this reduced the `fish/` directory from 303,726,938 bytes to 20,756,258 bytes — a 93.2% reduction — removing 463,382 Heartbeat events across 8,675 files in one pass. The migration is idempotent (a file with `lastCheckedAt` already populated and no Heartbeats left is written back byte-for-byte unchanged), which mattered in practice: a concurrent pipeline run from an unrelated, not-yet-rebased branch reintroduced Heartbeats into a subset of files mid-rollout, and a second migration pass cleanly compacted those too without disturbing anything already correct.

This also means PRD.md's "stays small by construction" claim is now true again in the way it always should have been — amended alongside this ADR to describe `lastCheckedAt` rather than "Change Event / Heartbeat history."

**Considered options**: keeping Heartbeats but pruning/compacting old ones on a rolling basis (rejected — still grows without bound between prunes, adds a second scheduled job and a second place "how old is too old" has to be decided, for a problem a single always-current pointer avoids outright); recording "last checked" only in `index.json` (where `Listing.lastObservedAt` already exists and already serves an equivalent purpose for the *current*, non-merged Listing) instead of on the history file's own per-Listing metadata (rejected — the chart only ever fetches one Canonical Fish's history file, not the ~37MB `index.json`; coupling the chart's gap logic to a second, much larger fetch for a value that logically belongs on the same record it's extending would be a worse-shaped dependency for no real benefit, and `index.json`'s Listing entries don't survive a same-Store merge or a cross-store repoint the way `CanonicalFishHistoryListing` entries already do).
