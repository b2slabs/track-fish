# Canonical Fish identity includes variety/color-morph, not species alone

ADR 0002 made Canonical Fish identity species-level and explicitly size/grade-independent. In practice, "species-level" was itself too coarse: real production data (issue #34) showed genuinely different, separately-marketed color morphs/varieties of the same species getting merged into one Canonical Fish — "Albino (Hifin) Cory", "Bronze Cory", and "Orange Venezuelan Cory" (all nominally *Corydoras aeneus*) landed in one group, and Medaka varieties ("Platinum Medaka", "Black Medaka", "Galaxy Medaka", ...) landed in another, worse, because most Medaka listings have no extractable scientific name at all and were purely fuzzy-matched on the shared base noun "Medaka". We decided two Listings only belong to the same Canonical Fish when they share both species (scientific name, when extractable) **and** variety — or both have no detected variety (plain/wild-type). Size, count, and sourcing terms ("School of 6", "Tank-Bred", "Locally Bred", quantity packs) remain excluded from identity exactly as ADR 0002 decided; only variety/color-morph is added as a second dimension.

Variety is detected by a curated keyword/pattern heuristic (`src/lib/variety.ts`) over the Listing's common name — colors (albino, bronze, platinum, ...), a handful of named patterns/morphs (galaxy, koi, marble, ...), and fin-type modifiers (hifin, longfin, sailfin, ...) — in the same spirit as `scientific-name.ts`'s binomial extraction: a heuristic with documented limitations, not a taxonomy. It deliberately does not scan descriptions (variety is reliably marketing copy in the title) and deliberately excludes geographic/origin qualifiers like "Venezuelan" (usually sourcing trivia, not a distinct product, per ADR 0002's own size/sourcing exclusion). The curated term list is not exhaustive: an unlisted strain name (e.g. many single-use Japanese Medaka cultivar names) is treated as "no detected variety" and such Listings can still over-merge with each other or with a genuinely plain Listing. This is accepted as a known limitation to be extended over time, the same way `canonical-fish-overrides.ts` accumulates maintainer fixes for cases the automatic signals get wrong.

**Considered options**: a full color/morph taxonomy with synonym resolution (rejected — same cost/benefit tradeoff ADR 0002 already rejected for size/grade normalization: a second messy, store-specific vocabulary to normalize before any comparison value is realized, for a problem a curated keyword list already resolves for the reported real cases); treating any wording difference as a different variety, i.e. reverting to pure fuzzy-name equality (rejected — would fragment genuinely identical Listings worded slightly differently by different Stores, re-creating the over-splitting ADR 0002 already guards against on the size axis).

## Addendum (issue #56): "Vietnamese White Cloud" is not a variety-detection gap

Issue #56 reported AquaHuna's "Vietnamese White Cloud" merging with plain "White Cloud" and asked whether this ADR's geographic/origin exclusion (above) should be narrowed — i.e., whether "Vietnamese" should join `VARIETY_TERMS` the way "Gold" (Golden White Cloud) already has.

Investigation found this is **not** a variety-detection gap: "Vietnamese White Cloud" is a genuinely different *species* (*Tanichthys micagemmae*), not a color/pattern variant of the White Cloud Mountain Minnow (*Tanichthys albonubes*) this ADR's identity rule is about. Every Store's own product copy for this item is explicit about the species difference (one even warns against mixing the two "to prevent hybridization"). Treating it as a variety would mean suffixing `:vietnamese` onto the *wrong* species slug (`cf:sci:tanichthys-albonubes`) — still taxonomically wrong, just wrong in a different, harder-to-notice way.

The real bug was two matching-pipeline issues, not this ADR's rule:
- `scientific-name.ts`'s last-resort "any parenthetical binomial in the description" heuristic can grab a contrastively-mentioned *other* species's name when a Store's copy mentions both binomials in the same paragraph (one Store wrote the correct name unparenthesized and the wrong one in parens).
- `canonical-fish.ts`'s fuzzy-rival-hijack guard (issue #16) can override a Listing's own, correctly-extracted *different* scientific name in favor of an already-established, cross-store rival when common-name wording is similar enough and the Listing's own id has no cross-store corroboration yet to protect it — exactly the AquaHuna Listing's situation.

Both real-dataset instances of "Vietnamese White Cloud" (AquaHuna, NU Aqua Shop) were repointed via `canonical-fish-overrides.ts` to `cf:sci:tanichthys-micagemmae` (see that file for the full per-Listing rationale). A broader sweep of other geographic-qualifier-tagged Listings in the real dataset (German Blue/Gold Ram, Peruvian/Amazon Angelfish, Thai Micro Crab, Japanese Trapdoor Snail, …) found every other instance to be exactly what this ADR already assumed: sourcing/locality trivia riding alongside the real distinguishing color/pattern word, all sharing one scientific name within the group. **Decision: this ADR's geographic-qualifier exclusion stands, unchanged.** "Vietnamese White Cloud" is the one real counterexample found, and it was a different kind of bug entirely — not evidence the exclusion rule itself is wrong.
